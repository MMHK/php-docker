## 1. Background & Goals

### 1.1 背景

本分支（`7.4-fpm`）因為 CVE-2026-109618 / CVE-2026-109619 必須從 PHP 7.4.33 原始碼重新編譯
（`php:7.4-fpm-bullseye` 已 EOL 且無法事後 patch binary）。既然 PHP 本體已經要編譯，
目前卻又在後續 `install-extensions.sh` 把 20 個擴充逐一 `phpize` 成 `.so`，等於：

- 同一批 extension source 被第二次編譯；
- 執行期多出 20 個 `.so` 與 20 個 `extension=` / `zend_extension=` ini；
- `.so` 全部要動態載入，啟動時多做一輪 dlopen / symbol resolve；
- `install-extensions.sh` 仍需處理 PECL tarball、依賴庫、重試與 IPE 版本，維護面較大。

現行 image 實測（`mmhk/php-docker:7.4-fpm`，本地 amd64）：

| 項目 | 實測 |
|---|---|
| extension dir（`no-debug-non-zts-20190902`） | 20 個 `.so`，合計約 4.2 MB |
| `/usr/src/php.tar.xz` | 10 MB（刻意保留給 `docker-php-source extract`） |
| `/usr/local/lib/php` | 11 MB（含 pear、opcache 等） |
| `docker history` 最底層 PHPIZE_DEPS apt layer | 約 284 MB（uncompressed） |
| 官方 `php:7.4-fpm-bullseye` | extension dir 只有 `opcache.so`、`sodium.so`，其餘全部靜態內建 |

> 官方 image 的組態就是「大部分擴充靜態、只有 OPcache 與 sodium shared」，
> 因此「把擴充 embed 進 php binary」在 PHP 7.4 是可行且成熟的做法，不是新發明。

### 1.2 Goals

1. 把**可靜態編譯**的擴充（預估 18 個）直接編進 `php` / `php-fpm` binary，
   執行期不再需要對應 `.so` 與 `extension=` ini。
2. 只保留 **OPcache 的 `opcache.so`**（PHP 7.4 的硬限制，見 2.2）。
3. 將「下載原始碼 → patch → 編譯 → 安裝 → 清除」收斂到**同一個 Docker `RUN`**，
   避免刪除後檔案仍留在前一層 layer（現行 image 的 284 MB / 10 MB 殘留問題）。
4. 提供類似 `docker-php-source` 的清除命令（`docker-php-clean`），
   支援 `source` / `deps` / `all`，供 Dockerfile 與手動除錯使用。
5. 維持現行功能與版本完全不變：
   - gd：JPEG / PNG / WebP / XPM / FreeType；
   - redis 6.0.2：lz4 + zstd；
   - memcached 3.4.0：json + sasl；
   - imagick 3.8.1：ImageMagick 6（bullseye 的 `libmagickwand-dev` 6.9.x）；
   - timezonedb 2026.5；
   - CVE patch 與所有 SHA256 pin 不變。

### 1.3 Non-Goals

- 不升級 PHP 版本、不改 CVE 補丁內容。
- 不新增/移除擴充清單（只改「編譯方式」）。
- 第一階段不改成 multi-stage builder（列為 7.3 的後續選項）。
- 不保證 image 內仍可 `docker-php-ext-install` 重新編譯 bundled extension
  （若選擇清除 build toolchain，見 5.3 的取捨）。

## 2. Feasibility Findings（已查證）

### 2.1 PHP 的靜態擴充機制

- 每個 bundled extension 的 `ext/<name>/config.m4` 最後呼叫
  `PHP_NEW_EXTENSION(<name>, <sources>, $ext_shared, ...)`。
  在 in-tree build 中，只要 configure 時**不給 `=shared`**，`$ext_shared` 就是 `no`，
  該 extension 會被放進 `EXT_STATIC`，由 `build/genif.sh` 產生
  `main/internal_functions.c`，於 `php_module_startup()` 時註冊。
- 因此可在 `./configure --enable-xxx`（或 `--with-xxx`）直接得到靜態內建，
  不需要 `phpize`，也不需要 ini。
- 對 PECL 套件（memcached / imagick / mcrypt / redis / timezonedb）：
  把 tarball 解到 `/usr/src/php/ext/<name>`，執行 `./buildconf --force`
  （release tarball 已含 parser/scanner，只需 autoconf），
  configure 的 `esyscmd(./build/config-stubs ext)` 就會納入新目錄。

### 2.2 OPcache 是硬限制

`ext/opcache/config.m4` 開頭明確寫著：

```m4
dnl Always build as shared extension
ext_shared=yes
```

且 PHP 官方手冊說明：**PHP 8.5 之前 OPcache 只能編譯成 shared extension**。
所以 `opcache.so` 必須保留，`zend_extension=opcache.so` ini 也必須保留。
這不是本方案可以繞過的部分。

### 2.3 其餘擴充的靜態可行性

| 擴充 | 來源 | 靜態可行性 | 备注 |
|---|---|---|---|
| bcmath bz2 exif ffi gd gettext mysqli pdo_mysql soap sockets zip snmp shmop | bundled 7.4.33 | ✅ `$ext_shared` 可為 no | 無 `PHP_ALWAYS_SHARED` |
| memcached 3.4.0 | PECL | ✅ `PHP_NEW_EXTENSION(..., $ext_shared)` | 需 libmemcached + sasl |
| imagick 3.8.1 | PECL | ✅ config.m4 有 `PHP_IMAGICK_STATIC` in-tree 分支 | 需 ImageMagick 6 |
| mcrypt 1.0.9 | PECL | ✅ | 需 libmcrypt |
| redis 6.0.2 | PECL | ✅ | 需 lz4/zstd 對齊現行 |
| timezonedb 2026.5 | PECL | ✅ 但需注意 include path | `ZEND_MOD_REQUIRED("date")`，需驗證靜態載入順序 |
| opcache | bundled | ❌ 強制 shared | 保留 `.so` |
| sodium | bundled | ✅ 可靜態 | 官方目前用 `--with-sodium=shared`；本方案可選擇一併內嵌 |

### 2.4 bullseye archive 的編譯依賴可用性（已用 apt-cache 實查）

`libbz2-dev`、`libffi-dev`、`libfreetype6-dev`、`libjpeg62-turbo-dev`、
`libpng-dev`、`libwebp-dev`、`libxpm-dev`、`libzip-dev`、`libsnmp-dev`、
`libmcrypt-dev`、`libmagickwand-dev`、`libmemcached-dev`、`libsasl2-dev`、
`liblz4-dev`、`libzstd-dev` 全部存在於 `archive.debian.org` bullseye。

### 2.5 Docker layer 的關鍵限制

Docker image layer 是 immutable：**在後續 `RUN` 刪除前一層的檔案，不會讓 image 變小**。
現行 Dockerfile 的第一個 `RUN` 安裝 `$PHPIZE_DEPS`（約 284 MB layer），
即使之後 purge，該 layer 仍在 image 裡；`php.tar.xz` 也是在下載 layer 產生，
之後 `docker-php-source delete` 只刪 `/usr/src/php`，tarball 仍留著。

→ 所以「縮小 image」不能只加一支 cleanup script，必須把
**安裝 build deps + 下載 + 編譯 + purge 全部放在同一個 `RUN`**。

## 3. Options Comparison

| 方案 | 內容 | 優點 | 缺點 | 結論 |
|---|---|---|---|---|
| A. **全靜態 + 單一 RUN 清除** | 18 個擴充進 php binary，只留 opcache.so；build deps 與 source 在同一個 RUN 內 purge | 一次編譯、runtime 最乾淨、可真正減少 layer | 需自管 PECL static 編譯與依賴清單；失去 in-container 重編 bundled ext 的能力（若 purge toolchain） | ✅ **建議** |
| B. bundled 靜態、PECL 維持 .so | 只把 13 個 bundled 擴充內嵌，PECL 仍交給 IPE | 風險較低、保留 IPE | 仍有 5 個 PECL `.so`、仍需 source tar 與 IPE、節省有限 | 次選（可作為階段 1） |
| C. multi-stage builder | builder 編譯，final stage 只 COPY `/usr/local` + runtime libs | 最大幅縮小、build 與 runtime 徹底分離 | Dockerfile 結構變動大；需重建 runtime apt 清單；arm64 CI 驗證成本高 | 後續選項（見 6.4） |
| D. 維持現狀 | 不改 | 無風險 | 重複編譯、20 個 .so、layer 殘留 | ❌ |

**建議採 A**，並把 C 當成第二階段（若 A 完成後仍覺得 image 太大）。
若擔心 PECL 靜態編譯風險，可先做 B，再把 PECL 併入 A。

## 4. Recommended Design (A)

### 4.1 目標 extension 清單

靜態內嵌（18）：

```
bcmath bz2 exif ffi gd gettext mysqli pdo_mysql soap sockets zip snmp shmop
memcached imagick mcrypt redis timezonedb
```

保留 shared（1 個，必須）：

```
opcache
```

可選一併靜態：

```
sodium
```

> 若 sodium 也靜態，extension dir 只剩 `opcache.so`；`php -m` 的模組清單不變。
> 建議先保留 sodium shared 以貼近官方行為，確認整條流程後再評估是否內嵌。

### 4.3 建置流程（單一 `RUN`）

```
RUN set -eux; \
    apt-get update; \
    apt-get install -y --no-install-recommends \
        $PHPIZE_DEPS patch \
        <PHP 本體既有 deps> \
        <上表 build deps>; \
    \
    # 1. 下載 + SHA256 驗證（不再單獨一層）
    curl -fsSL -o /usr/src/php.tar.xz "$PHP_URL"; \
    sha256sum -c ...; \
    \
    # 2. 解壓 + CVE patch（--fuzz=0）
    docker-php-source extract; \
    cd /usr/src/php; \
    patch -p1 --fuzz=0 < /usr/src/php-cve.patch; \
    \
    # 3. PECL tarball 下載 + SHA256 + 解到 ext/
    stage-pecl-sources; \
    \
    # 4. 重新產生 configure（納入 ext/*/config.m4）
    ./buildconf --force; \
    \
    # 5. 一次 configure + make + install
    ./configure <PHP 既有旗標> <4.2 的旗標>; \
    make -j "$(nproc)"; \
    make install; \
    strip; \
    \
    # 6. 只寫 opcache 的 ini（其餘擴充已內建）
    { echo 'zend_extension=opcache.so'; } > "$PHP_INI_DIR/conf.d/docker-php-ext-opcache.ini"; \
    \
    # 7. 清除 source / tarball / PECL staging
    docker-php-clean source; \
    \
    # 8. 保留 runtime libs，purge build deps（同一個 RUN）
    apt-mark auto '.*' > /dev/null; \
    apt-mark manual <runtime packages>; \
    apt-get purge -y --auto-remove ...; \
    rm -rf /var/lib/apt/lists/*; \
    \
    php --version; php -m; php-fpm -t
```

重點：

1. **不要**保留現行「先下載 php.tar.xz」的獨立 layer。
2. **不要**把 `$PHPIZE_DEPS` 安裝在 Dockerfile 最前面；搬進這個 build RUN。
3. `buildconf --force` 必須在 PECL source 放進 `ext/` 之後、configure 之前。
4. `make install` 後才 strip；strip 範圍與現行相同（`/usr/local` 下 `0111` 檔案）。
5. OPcache ini 必須保留；sodium 若維持 shared，也保留其 ini。

### 4.4 `docker-php-clean`（新增，放在 `docker-php-scripts/`）

介面比照 `docker-php-source`：

```sh
docker-php-clean source   # 刪 /usr/src/php、php.tar.xz、php-cve.patch、PECL staging
docker-php-clean deps     # 清 build deps（保留 runtime libs）
docker-php-clean all      # source + deps
```

行為：

- `source`：`rm -rf /usr/src/php /usr/src/php.tar.xz /usr/src/pecl /tmp/pecl-*`
- `deps`：先依 `ldd /usr/local/bin/php`、`php-fpm`、`composer` 等把 runtime 套件
  標成 manual，再 purge 上表的 `-dev` 套件與 `$PHPIZE_DEPS`；不要清掉
  `libxml2`、`libssl`、`libcurl`、`libsodium`、`libmagick*`、`libmemcached*` 等 runtime lib。
- `all`：兩者依序執行。
- 必須在**同一個 build `RUN`** 呼叫才對 image 大小有效；單獨在容器內執行只會縮小
  container writable layer，不會縮小 image layer。

> 建議將此腳本 COPY 進 `/usr/local/bin`，與 `docker-php-source` 並列；
> Dockerfile 內以 `docker-php-clean all` 收尾（或分兩段方便除錯）。

### 4.5 Dockerfile 需要移除 / 改寫的段落

| 現行段落 | 處置 |
|---|---|
| 最前面安裝 `$PHPIZE_DEPS` 的 `RUN` | 移除；改成 build RUN 內安裝，結束 purge |
| 獨立下載 `php.tar.xz` 的 `RUN` | 移除；下載移到 build RUN 內 |
| `RUN docker-php-ext-enable sodium` | 若 sodium 靜態則移除；若 shared 則保留 |
| `ADD install-php-extensions` | 移除（不再需要 IPE） |
| `COPY scripts/install-extensions.sh` + `RUN install-extensions.sh` | 移除；PECL 版本表併入 build script 或保留為資料檔 |
| `COPY docker-php-scripts/*` | 保留 `docker-php-source`；可移除 `docker-php-ext-install`（若不再支援 in-container 編譯） |
| `ENV PHPIZE_DEPS` | 可保留作為 build 清單，但 runtime 不再安裝 |

`entrypoint.sh`、FPM 設定、CA bundle、CVE marker、`USER www-data` 不變。

### 4.7 `docker-php-ext-static-install`（新增，比照 `docker-php-ext-install`）

**可以做，但必須先講清楚限制**：靜態內嵌不是「編一個 `.so` 丟進 extension dir」，
而是把 extension object 連進 `php` / `php-fpm`，因此**一定要有 PHP source tree、
原本的 configure 旗標與 linker**，並且要重新 link。這代表：

- 腳本可在 **builder stage**（或保留 toolchain/source 的 dev image）使用；
- 若 final image 已 `docker-php-clean all`（source + toolchain 都清掉），
  **腳本無法在 final image 內使用**，這是靜態內嵌的本質限制，不是腳本沒寫好。

介面設計（草案）：

```sh
docker-php-ext-static-install [-jN] [--configure-args "..."] ext-name [ext-name ...]
docker-php-ext-static-remove ext-name [ext-name ...]
```

行為：

1. 檢查 `/usr/src/php` 是否存在且已套 CVE patch；若只有 `php.tar.xz`，
   先 `docker-php-source extract`，並重新套用 `/usr/src/php-cve.patch`（`--fuzz=0`）。
2. 解析 extension 來源：
   - `ext/<name>/config.m4` 已存在 → bundled；
   - 參數是目錄或 tarball → PECL source，解到 `ext/<name>`；
   - 否則報錯（不在腳本內自動處理 PECL REST，避免舊問題）。
3. 把 ext 名稱加入 manifest `/usr/src/php/.docker-static-exts`。
4. 由 manifest 產生 configure 旗標：
   - 內建對照表覆蓋本 repo 的 18 個 ext（見 4.2）；
   - 未知 ext 先讀 `config.m4`：有 `PHP_ARG_ENABLE(<name>` → `--enable-<name>`；
     有 `PHP_ARG_WITH(<name>` → `--with-<name>`；否則要求 `--configure-args`。
5. 以「base configure args（Dockerfile 存的 `/usr/src/php/.docker-configure-base`）
   + manifest 產生的 ext flags」重新執行 `./buildconf --force` 與 `./configure`。
6. `make -j`、`make install`、strip；重新安裝 `opcache.so`（`--enable-opcache` 仍 shared）。
7. 跑 `php -m` / `php-fpm -t` 驗證；預設不自動清除，讓使用者可連續加 ext。
8. `--clean` 或建置結束時可呼叫 `docker-php-clean source`。

`docker-php-ext-static-remove` 只是從 manifest 移除後重跑同一流程；
不保證能完全移除已編進 binary 的 object，最終仍需重建 image 才乾淨。

> 這個腳本與 `docker-php-ext-install` 的差異：
> - 不產生 `.so`、不寫 `extension=` ini；
> - 需要重跑 PHP 的 configure/make，較慢但可增量（既有 `.o` 會重用）；
> - 需要先安裝該 ext 的 system deps（腳本不做 apt 依賴解析，這點與 IPE 不同）。


### 4.6 預期效果與量測方式

| 項目 | 現行 | 目標 |
|---|---|---|
| extension `.so` 數量 | 20 | 1（`opcache.so`）；若 sodium 也靜態則仍為 1 |
| `/usr/src/php.tar.xz` | 10 MB | 不存在 |
| `install-php-extensions` | 244 KB | 不存在 |
| PHPIZE_DEPS layer | 約 284 MB（獨立 layer） | 不再成為獨立 layer（同 RUN 安裝 + purge） |

## 5. Risks & Mitigations

| 風險 | 影響 | 對策 |
|---|---|---|
| PECL 擴充在 in-tree 靜態編譯失敗（include path、macro） | build 失敗 | 先在本地 PoC 逐一驗證 5 個 PECL；必要時對 `config.m4` 做最小 patch（例如 timezonedb 的 `-I$prefix/include/php/ext/date/lib`） |
| `buildconf --force` 改變 configure 行為 | 與官方 7.4.33 行為有差異 | 固定 autoconf 版本（bullseye 內建），並在 PoC 比對 `php -i` 的關鍵設定 |
| static 擴充無法 runtime 停用 | 無法用 ini 關閉個別擴充 | 可接受：image 本來就固定要這些擴充；以文件說明 |
| purge build deps 誤刪 runtime lib | php-fpm 啟動失敗 | 先跑官方 `ldd` + `dpkg-query --search` + `apt-mark manual` 流程，再 purge；用 `php -m`、`php-fpm -t`、實際 FPM 啟動驗證 |
| 失去 in-container 編譯能力（若 purge `$PHPIZE_DEPS`） | 使用者不能在容器內 `pecl install` / `docker-php-ext-install` | 明確列為取捨；若需要保留，改用 `docker-php-clean source` 僅清 source，不 purge toolchain |
| timezonedb 靜態載入順序 | 時區資料未生效或 startup 警告 | 驗證 `php -r 'echo timezone_version_get();'` 與 `php -m`；必要時保留 `timezonedb.so`（退回 B 方案） |
| arm64 build 差異 | CI 失敗 | 依現有 `ubuntu-24.04-arm` 原生 runner 驗證；不使用 QEMU |

- 方案 A 失敗時，回到目前的 Dockerfile（`git revert` 該 commit 即可）；現行 `install-extensions.sh`、IPE pin、php.tar.xz 流程仍完整。

  `$PHPIZE_DEPS`，先確保功能正確，再分階段處理體積。
